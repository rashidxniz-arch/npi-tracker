# NPI Tracker — engineering review and improvement plan

Review of `main` at `9d46819` (16 Nov 2026), done against `NPI_Tracker_AI_Review_Package.md`.
The fixes are on branch `improve/review-2026-11`. Nothing has been merged or deployed, and no Firebase data was read or written.

**Evidence labels** used throughout:
- **[Verified]** — read in the source, or reproduced by running the code.
- **[Inferred]** — likely, based on partial evidence.
- **[Runtime]** — needs a test against real Firebase or a real device.

Line numbers refer to `main` unless the text says otherwise.

---

## 1. Executive assessment

The tracker is a capable single-page PWA. It has proper per-user sign-in, Firestore rules that deny by default, HTML escaping on almost every render path, and a careful Email Intelligence rule engine with tests. The main risks were not crashes. They were silent data problems:

1. **Ticks and project updates attach to the wrong item after each snapshot publish.** Email actions and projects took their IDs from row position (`email-action-001`…). Status ticks and project updates are stored against those IDs, so any re-ordered or edited workbook moves every tick to a different action. **[Verified]**
2. **Anyone signed in could act as anyone else.** The "I am" menu changed the identity used in every write, and the Firestore rules only checked that the name was *a* team key, not *your* key. Ticks, updates, hours and audit entries could be recorded under another person's name. **[Verified]**
3. **The publisher could leave the tracker half-updated.** It deleted and rewrote three collections one after another, with no verify step, no concurrency check and no audit entry. A failure part-way showed a mix of old and new data. **[Verified]**
4. **Team-added tasks disappeared from the Actions list whenever an email snapshot was live.** **[Verified]**
5. **The "Latest Email Date" was used as the due date**, so most projects showed as overdue. **[Verified]**

All five are fixed on the branch and covered by automated tests. The rules changes still need one emulator run and one live check; see section 8.

Known limitation of content-based IDs:
- An action's ID comes from its project name and action text. If the wording changes between snapshots ("Send DFM" → "Send DFM rev 2"), it becomes a new action and its tick does not carry over.
- This is safer than the old behaviour, where every tick could move to a different action. Keeping wording stable in the workbook, or adding an `Action ID` column later, removes the limitation.

Fixed after an independent second review of the branch:
- **Excel dates one day early.** In Malaysia time, SheetJS dates came out a day early; afternoon serial numbers rounded to the next day. Dates now round to the minute, and serial numbers use floor. Tested in 4 time zones.
- **Positional legacy-ID fallback.** It could attach old ticks to the wrong item after the first versioned publish. Replaced by the content matching above.
- **Name-based identity fallback.** It disagreed with the rules. Identity now comes only from `users/{uid}.teamKey`; without it, the account is read-only and a banner explains why.
- **Over-eager date parser.** It read "2 decks" as 2 December and stopped at the first false hit. It now matches real month names only, keeps looking, and picks the nearest year when none is given.
- **Short project references.** These no longer link loosely.
- **Sign-in on network errors.** A network error no longer signs the user out.
- **Rollback.** It re-counts records before going live.
- **Rules.**
  - Viewers can't write audit entries.
  - A `failed` version can never be published.
  - The rules tests now cover the reassign, batch-plus-audit, publish-transaction and 400-record-batch cases.

Not changed, but noted:
- **Legacy encrypted data and Apps Script endpoint remain public.** `data/tracker.enc.json` (encrypted with the old shared passcode) is still published, and the old Apps Script endpoint is still in `config.js`. Retire both once the team signs off on Firebase (FIREBASE_SETUP step 7). The file also remains in git history. **[Verified]**
- **Admin pages are public URLs.** `migration.html` and `firestore-check.html` are reachable by anyone, but the rules protect the data, so the risk is low. **[Verified]**

## 4. Target architecture

```
Outlook (Graph, delegated Mail.Read)
   │  delta query per folder, watermark in Script Properties
   ▼
Apps Script processor (rules.js, M2.2.2)  ──►  emailCandidates/{messageHash}   (status: Candidate)
                                                   │  human review queue (admin page)
                                                   ▼  approve / edit / reject
                                              emailSnapshots/{version}/…  (status: staging → published)
                                                   │  transaction: emailSnapshotMeta/current.version
                                                   ▼
PWA (GitHub Pages) ──reads──► meta pointer → live version records + projects, tasks, status, updates, workload
        └──writes (as self)──► tasks, status, updates, workload, auditLogs   (rules: isMe + role)
latest.html (admin) ── manual Excel path → same staging/verify/switch flow
```

Principles:
- **One publish path.** Manual Excel and the future Outlook sync both write a staging version, so the dashboard has a single source of truth and a single rollback mechanism.
- **Facts separate from inference.** Email subject, date, extract and status text are shown as written. Stage, health and owner are labelled as rule-derived in the project pop-up.
- **No framework migration.** Plain ES modules with no build step are enough for this size.

## 5. Firestore publishing redesign (implemented in `latest.html`)

1. **Validate before anything is written.** `NPISnapshot.validate` checks:
   - required sheets and columns;
   - empty names;
   - over-long cells and the row limit;
   - duplicate keys;
   - actions or evidence that don't link to any project;
   - unreadable dates;
   - missing source message IDs.

   Errors block the publish; warnings are shown.
2. **Back up.** Download a JSON backup of the flat collections and the current live version. Publishing stays disabled until this is done.
3. **Stage.** Create `emailSnapshots/{asOf_timestamp_rand}` with `status:"staging"`, then write `projects` / `actions` / `evidence` subcollections in batches of 400. Record IDs are content hashes, so the same project or action always gets the same ID.
4. **Verify.** Read back the counts of all three subcollections. Any mismatch aborts, marks the version `failed`, and leaves the live snapshot untouched.
5. **Switch.** One transaction does all of the following:
   - reads `emailSnapshotMeta/current`;
   - checks that the live version is still the one seen when the page loaded (optimistic concurrency — a concurrent publish aborts);
   - sets the pointer;
   - marks the new version `published` and the previous one `superseded`;
   - writes an `auditLogs` entry.
6. **Mirror (transition only).** Optionally rewrite the old flat collections, so phones still on v2.11 see the new data. A mirror failure does not affect the live version.
7. **Rollback.** "Make live" on any earlier published or superseded version runs the same transaction, with audit action `snapshot_rolled_back`.
8. **Immutability.** The rules allow records only while a version is `staging`; records can never be updated or deleted; the pointer can't be deleted. Only `status` / `publishedAt` / `publishedBy` / `error` may change on a version.

`projects` and `tasks` are never touched by the publisher. **[Verified by smoke test]**

## 6. Outlook sync design (not implemented — design only)

The Refresh button does **not** fetch Outlook. No end-to-end Outlook → Firestore pipeline exists. **[Verified]**

1. **Read.** Use Microsoft Graph with delegated `Mail.Read` (already tested). Run a delta query per folder (`/me/mailFolders/{inbox|sentitems}/messages/delta`) and store the `@odata.deltaLink` in Script Properties. Page with `@odata.nextLink` and process at most N messages per run, so runs stay inside Apps Script's 6-minute limit.
2. **Identity and idempotency.**
   - Key every message by `sha256(internetMessageId)`, with Graph `id` as a fallback. This is the existing `m23ProcessEmail_` pattern: create-if-missing, deterministic insight IDs, and the marker written last.
   - Updated messages (delta returns them again) overwrite the candidate only if `lastModifiedDateTime` is newer.
   - Deleted messages (`@removed` in delta) mark candidates `sourceDeleted` and are never published.
   - Forwarded and reply chains are grouped by `conversationId`. Only the newest message per conversation feeds the project summary; older ones remain evidence.
   - Duplicate copies (the same internetMessageId in Inbox and Sent) collapse to one hash.
3. **Approval.**
   - Candidates land in `emailCandidates` (admin-only) with:
     - `confidence`;
     - `matchedBy` (explicit-id / keyword / unmatched);
     - the rule-derived fields, labelled as inferred;
     - the source fields (subject, date, sender domain, extract), labelled as observed.
   - An admin review page lists unmatched or low-confidence items first. Approving builds a staging version through §5, so publishing stays atomic and auditable.
4. **Privacy.**
   - Store the subject (truncated), the sender domain (not the full address) and short extracts only.
   - Exclude HR and personal content with the existing skip rules.
   - Put a retention limit on candidates (e.g. 90 days).
5. **Sync Now.**
   - The button should call an authenticated Apps Script endpoint that only *queues* a run, so it returns at once; the run's status is then shown on the page.
   - Until this exists, the UI wording must keep saying "reload published snapshot".
6. **Tests.**
   - Fixture-based Graph responses: new, updated, deleted, forwarded and duplicate messages.
   - Idempotency: running the same batch twice must produce the same documents.
   - Watermark recovery after a failed run.

## 7. UI/UX recommendations

Done on the branch:
- Snapshot age is shown in the name menu, on the Email page and on the Updates page. A banner appears after 7 days.
- The project pop-up states where its status came from (email status text, latest email date) and which fields are rule-derived.
- Unassigned actions are grouped as "Not matched to a team member", with the original text in a tooltip.
- Action rows show the due date from the snapshot, in red when it has passed.
- Read-only accounts see a banner and disabled controls, not "Permission denied" errors.
- Sign-in survives reloads. Error messages cover too-many-attempts and offline cases.
- The publisher shows a step-by-step progress list, a validation report and a versions table with rollback.

Recommended next:
- **Actions view.** Add "My actions" as the default for members. Add a due-date sort and an overdue filter. With 30–50 concurrent actions, grouping by person alone is slow to scan.
- **Projects table.** Add a "Last email" column and a "stale > 14 days" chip, so quiet projects stand out.
- **Offline.** The Firebase SDK is cross-origin and not cached, so the app shell opens offline but can't sign in. Either cache the SDK files in the service worker or show a clear "You're offline" lock-screen message.
- **Accessibility.**
  - The tooltip uses `role="tooltip"` but is mouse/focus only. Make sure every chart bar's content is also available as text; the pipeline buttons already have `aria-label`s.
  - Check contrast of the pale tags (`.tag` on `#EAF3FF`) against WCAG AA.
- **Empty and error states.** "Rashid's Claude will add new ones" (project empty state) is no longer accurate. Point to the snapshot publish instead.
- **Mobile.** Bottom navigation has 7 destinations; consider moving Workload and Email Intel under a "More" sheet.

## 10. Do-not-change list

- The `projects`, `tasks`, `status`, `updates`, `workload`, `meetings`, `team`, `users` and `auditLogs` collections and their existing documents. The publisher never touches them.
- Existing ticks stored under `email-action-NNN` IDs. They keep working through the legacy-ID fallback; do not bulk-rename them.
- Firebase email/password sign-in with admin-provisioned accounts and `users/{uid}.active` gating.
- Default-deny rules (`match /{document=**}`) and admin-only snapshot writes.
- The evidence-based Workload page and its rule that action count alone never means overload.
- The read-only nature of Email Intelligence, and the separation of observed email content from rule-derived inference.
- The service-worker update prompt (`SKIP_WAITING` only on user action) and the "What's new" history.
- The rule engine's privacy choices: no full email bodies, sender domain only, hashed message IDs.
- No secrets in the repository: the Firebase web config is public by design; Admin SDK keys and OAuth tokens must never be committed.
